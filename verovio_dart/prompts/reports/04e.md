## Desvios do C++ introduzidos

- **Largura de texto/glifo.** `AdjustHarmGrpsSpacingFunctor` e `AdjustTempoFunctor` leem o content
  box de um `FloatingPositioner` de `Harm`/`Tempo`; em produção esse box vem de
  `headless_extents.dart`'s `_processPointControlEvent`, que ancora `x1 == x2` (largura zero) para
  eventos pontuais — únicos exercitados pelo corpus desta tarefa (todos os `<harm>`/`<tempo>` usam
  `@tstamp` ponto, não `@tstamp`/`@tstamp2` de intervalo). `Syl` nunca recebe content box alguma em
  modo headless (nenhum branch de `headless_extents.dart` trata `ClassId.syl`), então
  `AdjustSylSpacingFunctor`'s filtro `HasContentHorizontalBB()` sempre esvazia a lista de sílabas.
  Isso é exatamente a lacuna antecipada pelo prompt (`headless_extents.dart:593`/`:658`, tarefa
  05-12); a lógica portada é fiel ao C++ para o caso de bounding box vazia, e a paridade real foi
  verificada com árvores sintéticas que reconstroem o content box a partir dos valores do fixture
  (ver `test/adjust_harm_tempo_syl_test.dart`), como já fora feito no relatório 04d para o gap de
  `BeamSegment::CalcBeam`.
- `Syl::CalcHyphenLength` (largura de hífen via `Doc::GetTextGlyphWidth`, fonte de texto real) e o
  ramo de elisão de `Syl::CalcConnectorSpacing` (`Doc::GetGlyphAdvX` da fonte musical) são
  aproximados a partir da unidade de desenho — nenhum dos dois é exercitado por `lyric-001.mei`/
  `lyric-004.mei` (nenhum `@wordpos="i"/"m"`, nenhuma elisão neles), então a aproximação não afeta
  os números desta tarefa; documentado inline em `calcHyphenLength`.

## Achados fora de escopo

Três lacunas pré-existentes (nenhuma introduzida por esta tarefa, nenhuma corrigida aqui — todas
em código de fases anteriores) surgiram ao comparar a execução em produção com os fixtures:

1. **`AttNIntegerComparison` nunca casa um `@n` ausente — `AdjustSylSpacingFunctor` nunca visita
   um `Verse` de verdade em produção.** `InitProcessingListsFunctor.visitStaff`
   (`preparedata_functor.dart`) monta a árvore de versos com `verse.n ?? 0`, mas
   `AttNIntegerComparison.call` (`comparison.dart:178-184`) compara `element.n == n` — e
   `AttNInteger.n` é `int?`, ficando `null` (não `0`) quando `@n` está ausente. `null == 0` é
   sempre falso, então o `Filters` de `staff`/`layer`/`verse` nunca deixa a travessia alcançar (nem
   descer até) um `<verse>` sem `@n` — o caso comum (`lyric-001.mei` e `lyric-004.mei`, como todo o
   resto do corpus de letra, não têm `@n` em `<verse>` porque há uma única linha). O C++ não tem
   esse problema porque `AttNInteger::GetN()` já devolve `MEI_UNSET` (um `int` de verdade, não um
   "nulo") quando o atributo está ausente — os dois lados da comparação usam o mesmo sentinela.
   Isso não afeta só esta tarefa: o mesmo padrão de filtro já existia antes dela, em
   `doc.dart:1219-1234` (`PrepareLyricsFunctor`, ligação de conectores de sílaba) — ou seja, ligar
   conectores de palavra por sílaba também está quebrado para verso sem `@n`, desde antes desta
   tarefa. Corrigir isso corretamente parece exigir trocar `AttNInteger.n`/`AttNNumberLike.n`'s
   representação para usar `meiUnset` como default em vez de `null` (ou ensinar
   `AttNIntegerComparison` a tratar `null` como o sentinela) — uma mudança em código gerado/attrs
   compartilhado por muitos functors, fora do escopo desta tarefa. Recomenda-se uma tarefa dedicada.
2. **`harm/harm-001.mei`: deslocamento constante por compasso, não relacionado à largura de
   texto.** Comparando os `drawingX` que o port calcula para os 13 `<harm>` (todos `@tstamp`
   pontuais, sem `@startid`) contra o `contentLeft` do fixture (que tem `contentX1 == 0` em todo
   registro, ou seja, `contentLeft` É a posição do harm no C++): no compasso 1 a diferença é
   **exatamente 636** para as 5 harms (852-216, 1902-1266, 3642-3006, 4332-3696, 5022-4386) — um
   deslocamento constante, não uma divergência de largura de texto (que variaria harm a harm). Isso
   indica uma divergência de alinhamento pré-existente — provavelmente no espaço reservado para a
   claves/armadura/fórmula de compasso inicial de uma partitura com `<staffGrp symbol="bracket">`
   de 3 pautas — anterior a esta tarefa e não corrigível dentro do seu escopo (o functor desta
   tarefa não toca nenhum código de alinhamento inicial). Como a diferença é constante dentro do
   compasso, ela se cancela nas subtrações consecutivas que `AdjustHarmGrpsSpacingFunctor` faz — a
   fórmula do `overlap` fica correta *relativamente*, só a largura de texto ausente (achado
   principal, acima) contamina o valor absoluto.
3. **`tempo/tempo-001.mei`: o `<tempo>` está num compasso de anacruse (`type="upbeat"`) cujo
   `@tstamp="1"` nunca é resolvido.** `doc.layOut()` emite `Warning: 1 time pointing element(s)
   could not be matched in measure ...` para este arquivo (mensagem de
   `PrepareTimePointingFunctor.visitMeasureEnd`, `preparedata_functor.dart:721-726`) — mas essa
   função só trata `@startid` (retorna cedo se `!interface.hasStartid`); a resolução de `@tstamp`
   é responsabilidade de `PrepareTimestampsFunctor`/`TimestampAligner`, que aparentemente não
   resolve corretamente o tstamp=1 dentro do compasso de anacruse (2 colcheias antes do primeiro
   compasso numerado). O efeito: `tempo.getStart()` acaba noutra posição (`start=180` em vez do
   `1305` do C++), então mesmo com a fórmula de `AdjustTempoFunctor` correta (verificada à parte,
   epsilon 0, numa árvore sintética) a produção diverge. Fora do escopo desta tarefa (pertence à
   fase de preparação de tempo/tstamp, não ao ajuste horizontal).
