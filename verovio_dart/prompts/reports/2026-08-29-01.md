### Parte 1 — o guard de `View::DrawTempo`

`lib/src/rendering/view_control.dart:2406` (`drawTempo`) — **+11 / −7 linhas**. O port tinha:

```dart
dynamic start;
try {
  start = (tempo as dynamic).getStart();
} catch (_) {
  return;
}
```

O C++ (`view_control.cpp:2741`) tem:

```cpp
// Cannot draw a tempo that has no start position
if (!tempo->GetStart()) return;
```

São condições **diferentes**: o Dart retornava quando `getStart()` *lançava*; o C++ retorna quando
o valor *é nulo*. Trocado por:

```dart
final Object? start = (tempo as dynamic).getStart() as Object?;
if (start == null) return;
```

O `try/catch` era além de errado, **inalcançável**: `Tempo` faz mixin de `TimePointInterface`, cujo
`getStart()` é leitura de campo e não lança, e `drawControlElement` (`view_control.dart:106`) só
despacha para cá sob `isClass(ClassId.tempo)`. Com o caso nulo caindo através do guard, a execução
chegava a `start as Object` (`:2479`) e estourava.

## Divergências em aberto

**Nenhuma nova.** Uma suspeita levantada durante a tarefa foi investigada e **descartada**, e vale
registrar porque o caminho é contraintuitivo:

`note/note-005.mei` — o arquivo que quebrava — tem `<tempo staff="1" tstamp="1">Largo</tempo>`, sem
`@startid`. Como o golden do C++ desenha o tempo (`class="tempo"`, texto "Largo"), a hipótese era
que o start nulo fosse uma segunda divergência, na resolução de `@tstamp`, e que o guard novo
estivesse escondendo-a ao pular o desenho.

Medido, não é:

| Momento | `getStart()` |
|---|---|
| após `import` | `null` |
| após `prepareData()` | `timestampAttr` |
| após `layOut()` | `timestampAttr` |

E o SVG final do Dart contém `class="tempo"` e "Largo", igual ao C++.

O nulo é **transitório**: `drawTempo` também roda em passadas intermediárias de bounding box
(`Page::LayOutHorizontally` → `_renderBoundingBoxes`, dentro de `castOffDocBase`), antes de o
timestamp estar resolvido naquela árvore. É exatamente a situação para a qual o guard do C++
existe — o comentário dele, "Cannot draw a tempo that has no start position", descreve um estado
normal do pipeline, não um erro de dados.

## Armadilha encontrada: `dart format` em `view_control.dart`

O §3 do MESTRE manda formatar "só os arquivos da sua tarefa". Isso pressupõe que o arquivo editado
já esteja formatado — e `view_control.dart` **não estava**. Rodar
`dart format lib/src/rendering/view_control.dart` produziu um diff de **1670 linhas** para uma
mudança de 16, soterrando-a.

Desfeito: o arquivo foi restaurado ao conteúdo do HEAD e a mudança semântica reaplicada à mão. Diff
final: **16 inserções, 6 remoções**.

Efeito colateral que quase passou: a formatação normalizava `catch(_)` (sem espaço) para
`catch (_)`, e o critério 5.2 do portão — que conta a string literal — **subiu** de 820 para 828
ocorrências logo depois de eu ter *removido* uma. O número não media o que parecia medir.

**Recomendação para a 05-34b e a 05-35**, que vão reescrever esses arquivos inteiros: formate num
commit separado do commit de conteúdo, ou não formate. E ao ler os critérios 5.1/5.2 do portão,
lembre que eles contam texto: uma reformatação mexe no número sem mexer no código.
