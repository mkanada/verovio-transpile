## Desvios do C++ introduzidos

1. **`extension ViewPage on View` dentro do `part`** — padrão da 05-06/05-07
   registrado nos doc comments dos dois arquivos.
2. **`m_drawingScoreDef = m_currentPage->m_drawingScoreDef` (cópia) →
   `drawingScoreDef.copyFrom(...)`**: o campo `View.drawingScoreDef` é
   `final` e o Dart só tem referências — a cópia é explícita (desvio já
   anunciado no doc comment de `view.dart` na 05-06).
3. **Os stubs `_notYet` lançam `UnimplementedError` onde o C++ desenha**:
   `drawCurrentPage` interrompe a renderização no primeiro método ainda não
   portado (`DrawScoreDef`, e no fim da página `DrawRunningElements`). A
   saída parcial até o ponto do lançamento é idêntica à do C++, e o
   `getStringSVG()` do `SvgDeviceContext` serializa a árvore construída até
   ali. O `DrawRunningElements` real (05-19) é no-op para páginas sem
   header/footer, como o C++.
4. **`Object.isMilestoneElement` usa checagens nominais dos mixins**
   (`is SystemMilestoneInterface`) no lugar dos `dynamic_cast` do C++ — os
   mixins são aplicados exatamente onde o C++ tem as interfaces.
5. **`DrawSystemDivider`/`FindDescendantByType(MEASURE, 1, BACKWARD)`**: o
   `findAllDescendantsByType` do Dart não implementa a direção `BACKWARD`
   (parâmetro `direction` de `findDescendantByType` é ignorado — defeito
   pré-existente); o port pega o `.last` da lista com `deepness: 1`, mesmo
   resultado para a mesma profundidade.
6. **`TextListInterface.getText()` acessa `(child as dynamic).text`**: o
   C++ faz `vrv_cast<Text *>`; importar a classe `Text` gerada de
   `object.dart` criaria um ciclo interno do modelo — o cast dinâmico tem o
   mesmo efeito em runtime sobre a lista já filtrada (o `assert(text)` do
   C++ é subsumido pelo filtro `lb`/`text`).
7. **`UTF32to8(annot->GetText())` → `annot.getText()`**: strings Dart já são
   texto; `DeviceContext.addDescription` recebe `String`.
8. **`background` de `DrawCurrentPage` é parâmetro sem uso**, como no C++
   (o único uso está na linha comentada view_page.cpp:89) — mantido pela
   assinatura (view.h:157).
9. **Stubs com assinatura fiel, exceto `BarLine`**: `drawScoreDef` tipa
   `barLine` como `Object?` até a 05-09 portar a assinatura real (evitou
   importar `BarLine` sem uso, que o analyzer rejeita); documentado no doc
   comment do stub.

## Achados fora de escopo

1. **`findDescendantByType(..., direction: backward)` ignora a direção**
   (`lib/src/model/object.dart:865-871`): o parâmetro `direction` existe na
   assinatura mas `_traverse` é sempre chamado com `forward`. Nenhum
   chamador atual passa `backward`; o `DrawSystemDivider` contorna com
   `.last` (desvio 5). Corrigir o `findDescendantByType` (e revisar os
   chamadores) é refactor de modelo fora desta fatia.
2. **`Annot.isSupportedChild` devolve `true` incondicionalmente**
   (`lib/src/model/editorial_element.dart`), enquanto o C++ só aceita
   `annot` e elementos de texto (annot.cpp:35-46). Pré-existente; nenhum
   leitor depende disso hoje.
3. **`PageMilestoneEnd`/`SystemMilestoneEnd` copiam o `id` do start no
   construtor Dart** (`system_page_elements.dart:286-291` e `:317-321`),
   enquanto os construtores C++ não tocam no id (pagemilestone.cpp:28-33 e
   systemmilestone.cpp:28-33 — cada end gera id próprio; visível no golden:
   `class="pageMilestoneEnd q14gtc1t"` com id `dzj5nv5` ≠ id do score). O
   comentário do `SystemMilestoneEnd` Dart até alega espelhar o
   construtor C++. A comparação estrutural normaliza ids posicionais, então
   não afeta o harness; registrado para a fase de igualdade de ids (05-25).
