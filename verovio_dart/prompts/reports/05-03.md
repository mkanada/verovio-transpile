## Desvios do C++ introduzidos

1. **`drawSvgShape(String svg)`** — o C++ recebe `pugi::xml_node`
   (`Svg::Get()`) e faz `append_copy` dos filhos; o modelo Dart `Svg`
   guarda o conteúdo como string (decisão de fase anterior), então a
   assinatura leva string e o método parseia com `parseMeiXml`, copiando
   os filhos da raiz com `MeiXmlNode.copy()`. Falha de parse espelha nó
   nulo (nada é copiado). Documentado no doc comment.
2. **`drawSvgBoundingBox` sem `View *`** — o parâmetro `View *view` não é
   representável (a classe `View` chega na 05-06). As duas conversões que
   o corpo pede à view (`ToDeviceContextX/Y`, view.cpp:72/:84) são
   injetadas como funções; `null` espelha `View *` nulo (o corpo não faz
   nada além do guard `m_svgBoundingBoxes && view`), que é o estado atual
   das chamadas de `endGraphic`/`endTextGraphic`. O corpo completo existe
   e é exercido pelos testes com conversões falsas (identidade X, flip Y
   contra `contentHeight`). Emenda explicitada para a 05-06/05-12.
3. **Visibilidade** — `DrawSvgBoundingBoxRectangle`, `DrawSvgBoundingBox`
   e `GetColor` são privados no C++; públicos no port para os testes
   alcançarem os dois primeiros antes da View existir (mesmo precedente
   de `appendIdAndClass`, da 05-02).
4. **Código morto espelhado** — os ramos `groupInPage` e `drawAnchors`
   (flags falsas no C++ também) foram portados por fidelidade e marcados
   com `// ignore: dead_code`, que o flow analysis do Dart deduz a partir
   da atribuição local constante.
5. **Opacidade `double` × `float`** — o C++ guarda opacidade como `float`
   e o pugixml imprime o `double` promovido com `%.9g`; o port guarda
   `double` e imprime com o mesmo `%.9g`. Para valores de uso real
   (1 casa decimal) a saída é idêntica; divergência só ocorreria num
   `float` cujo 9º dígito significativo sobreviva à promoção, caso não
   produzido por nenhum caminho do port.
