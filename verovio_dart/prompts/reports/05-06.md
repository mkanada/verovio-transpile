**Decisão de particionamento** (registrada também no doc comment do
`view.dart`): **`part` / `part of`**, não `extension`. Cada `view_*.cpp` do C++
vira um `part` do library `view.dart` nas tarefas seguintes (`view_graph.dart`,
`view_page.dart`, ...). Justificativa: o C++ divide **uma classe** por vários
arquivos; um `part` permite definir os métodos da mesma `View` em outro arquivo
compartilhando a privacidade do library (`_currentOffsets`, `_Offset`, e os
statics de ligadura que virão), que é exatamente a visibilidade de membro
privado do C++ para todos os `view_*.cpp`. `extension` não adiciona campos, não
acessa privados do library e mudaria o dispatch. As diretivas `part` serão
acrescentadas à medida que os arquivos surgirem (05-07 em diante).

## Divergências em aberto

Nenhuma na aritmética portada. Um comportamento do C++ fica temporariamente
achatado (documentado no doc comment de `setPage`): no ramo
transcrição/facsimile de `SetPage(doLayout=true)`, o C++ chama
`Page::LayOutTranscription` (page.cpp:249), que não está portada (o corpo dela
termina num render pass com `BBoxDeviceContext` que reentra no `View`,

layout já está feito. Atinge apenas quem chamar `setPage(..., true)` sobre um
doc em modo transcrição antes da 05-12; o caminho do `BBoxDeviceContext`
(`doLayout = false`) não é afetado.

## Desvios do C++ introduzidos

1. **Particionamento por `part`** (decisão da tarefa, acima) — sem efeito no
   comportamento; registrado no doc comment do library.
2. **Métodos privados ficam públicos**: `StartOffset`, `EndOffset`,
   `SetOffsetStaffSize`, `CalcOffset*` e `IntTo*Figures` são privados no C++
   (view.h:605-672); públicos no port para os testes exercitarem a aritmética
   diretamente — o mesmo padrão adotado na 05-05 para `getPenWidthOverlap()`.
3. **`View::Offset` → `_Offset` biblioteca-privada**: Dart não tem classe
   aninhada; privada no library é visível aos futuros `part`s, exatamente como
   a classe privada do C++ é visível a todos os `view_*.cpp`. (O prompt pedia
   "`class View`, `class Offset`"; a forma privada é a mais fiel — a struct não
   faz parte da API do C++.)
4. **`int &x, int &y` → retorno de valor**: `calcOffset` devolve o registro
   `(int, int)`; `calcOffsetX/Y` e os `calcOffsetSpanning*` devolvem o `int`
   ajustado; `calcOffsetBezier` muta os `Point` da lista in place (campos
   mutáveis), preservando a semântica de referência do array do C++. A
   truncagem para `int` acontece em cada passo, como na atribuição do C++.
5. **`std::u32string` → `String` UTF-16**: os dígitos SMuFL (≥ 0xE080) saem
   como pares substitutos; os code points são idênticos (os testes comparam
   `.runes`). `unsigned short number` vira `int`.
6. **`GetSlurHandling`/`SetSlurHandling`** (view.h:176-177) e os membros
   protected (`m_currentColor`, `m_slurHandling`, `m_drawingScoreDef`) viram
   campo público — Dart não tem `protected`.
7. **`m_drawingScoreDef`** continua sendo uma **cópia** (o alerta do prompt):
   o campo é `final ScoreDef drawingScoreDef = ScoreDef()` — instância própria,
   como `Page.drawingScoreDef` (doc.dart); quem preencher deve copiar estado
   (ex.: `copyFrom`), nunca atribuir por referência. Documentado no doc
   comment do campo; a cópia em si acontece em `DrawCurrentPage` (05-08).
8. **`assert(page)` de `SetPage`** subsumido pelo parâmetro não-nulável;
   `assert(interface)` de `StartOffset` subsumido por `hasInterface` garantir o
   cast (o C++ precisa do assert porque `GetOffsetInterface()` pode devolver
   NULL).
9. **Destrutor virtual `~View`** sem equivalente (Dart tem GC); nenhum recurso
   não-gerenciado na classe.

## Achados fora de escopo

1. **Os elementos de controle gerados não registram `InterfaceId.offset`
   (nem `altSym`/`linking`)** — medido neste ambiente:

   ```
   Dir: offset=false offsetSpanning=false
   Hairpin: offset=false offsetSpanning=true
   Slur: offset=false offsetSpanning=true
   Accid: offset=true offsetSpanning=false
   Custos: offset=true offsetSpanning=false
   ```

   No C++ o construtor de `ControlElement` registra as três interfaces para
   todos os elementos de controle (controlelement.cpp:39-41) e `Dir::Dir`
   acrescenta TextDir/TimeSpanning (dir.cpp:44-45) — `HasInterface(
   INTERFACE_OFFSET)` é verdadeiro para `Dir`. No port, `ControlElement.reset()`
   (control_element.dart:43-66) registra `altSym`/`linking`/`offset`, mas o
   `reset()` que efetivamente roda nas classes geradas resolve para o último
   mixin da cadeia que o declara: `TimeSpanningInterface.reset()` chama
   `super.reset()`, que cai em `TimePointInterface.reset()`
   (time_interface.dart:34) — que **não chama `super.reset()`** — e a cadeia
   morre antes de `ControlElement.reset()`. Efeito colateral do mesmo nó: os
   campos que só `ControlElement.reset()` limpa (`ho`, `vo`, `color`, `label`,
   `type`, `altsym`, `next`, `sameas`, `corresp`, `copyof`) não são limpos num
   `Dir.reset()`. Impacto no View: o ramo `InterfaceId.offset` de
   `startOffset` não dispara para elementos de controle (o de spanning
   funciona, porque `Hairpin`/`Slur`/`Tie` registram `offsetSpanning` nos
   próprios construtores). Os testes desta tarefa exercitam o ramo via
   `Accid`/`Custos` (que registram `offset` nos próprios construtores,
   layer_elements_gen.dart:88+). Arranjar a cadeia de `reset()` dos mixins é
   refactor do model inteiro — tarefa própria, urgente antes da 05-20
   (view_control.cpp), onde `StartOffset` é chamado com elementos de controle.

2. **Tabela de status em `prompts/README.md`**: as linhas 05-01 a 05-04 seguem
   ☐ apesar de concluídas (mesmo apontado na 05-05). Marquei apenas a 05-06
   (minha fatia).

3. **O prompt sugere `grep -n "ppuFactor\|..." lib/src/model/doc.dart`** — no
