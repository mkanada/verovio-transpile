## Desvios do C++ introduzidos

1. **`zip_file_reader.dart` (novo):**
   - `Load(filename)` lê via hook plugável `resourceBytesReader` em vez de
     `std::ifstream`; no web o stub devolve `null`. O caso EMSCRIPTEN
     (data URI/base64) fica a cargo do reader instalado pelo app.
   - `LoadBytes` devolve `false` se os bytes não decodificam; o C++
     constrói `miniz_cpp::zip_file` sem validar e sempre devolve `true`
     (falharia depois nos acessores).
2. **`getCustomFontname`:** o C++ escolhe variante com
   `#ifdef __EMSCRIPTEN__` (desktop: stem do filename; emscripten: varre a
   lista de arquivos do zip). Dart não tem compilação por alvo: a varredura
   do zip (emscripten) vem primeiro e o stem do filename é o fallback. No
   layout padrão de fontes custom (`<Name>.xml`/`<Name>.css` na raiz do
   zip) as duas variantes coincidem; no desktop C++, um zip cujo nome
   difere do XML interno falha depois em `LoadFont` de qualquer forma
   (`<stem>.xml` não está no arquivo), então a ordem de varredura só passa
   a carregar o que o C++ rejeitaria.
3. **`loadAll`:** iteração de diretório via hook plugável
   `resourceDirectoryLister`; resultado `null` (diretório ausente ou stub
   web) conta como diretório vazio — `std::ranges::all_of` sobre intervalo
   vazio também é `true`. O C++ não capturaria a exceção de
   `directory_iterator` para path inexistente.
4. **Helpers privados** `_fileNameOf`/`_parentOf`/`_stemOf`/`_extensionOf`
   em `resources.dart` não têm contraparte no C++ (substituem
   `std::filesystem::path`); são auxiliares do port, privados e
   documentados como tais (regra de higiene 3).
